# 1. Identification and Significance of the Problem / Operational Need

### 1.1 Operational Context & The Multi-Sensor Fragmentation Trap
Modern United States Navy surface combatants—such as Arleigh Burke-class destroyers operating in contested tactical chokepoints—depend on continuous, high-integrity Positioning, Navigation, and Timing (PNT) data to execute navigation, combat system targeting, radar synchronization, and distributed tactical operations [GAO-21-320SP p.1; OPNAVINST 9420.1C §4]. To counter growing electronic warfare (EW) threats, naval platforms ingest PNT data across disaggregated sources including GPS (SPS/PPS/M-code), Inertial Navigation Systems (INS), eLoran, radar range fixes, optical tracking, and atomic clocks [GAO-21-320SP p.12; ION GNSS+ 2023]. 

However, current shipboard architectures present these disparate PNT feeds across isolated consoles and raw sensor status indicators [DON26BX05-NP004 Description]. In contested electromagnetic environments, operators face a fragmented operational picture: raw C/N0 drops, RAIM alarms, and position jump alerts flash independently across un-correlated screens [MSC.302(87) §5; PNT-Integrity C4]. Under intense operational stress, bridge watchstanders and Electronics Technicians (ETs) must manually cross-check sensor diagnostics, calculate residual discrepancies, and infer root-cause anomalies while executing collision-avoidance maneuvers. This manual processing creates severe cognitive overload, delays tactical decisions, and risks misidentifying sophisticated spoofing attacks as temporary hardware faults [DON26BX05-NP004 Description; Q&A 8/26/26].

### 1.2 The Load-Bearing Threat: Coherent Regional Bias Capture
The critical vulnerability in contemporary navigation is non-independent RF spoofing. In a coherent regional bias attack, an adversary broadcasts synchronized synthetic GNSS signals that capture multiple shipboard GNSS receivers simultaneously [NIST IR 8323r1 p.18; DHS PNT CF v2.0 §3.2]. Because both receivers process the same corrupted RF environment, intra-receiver RAIM and cross-receiver position checks read as mutually consistent and "Assured" [MSC.1/Circ.1575 §4; PNT-Integrity C4]. 

Legacy systems relying solely on cross-receiver agreement fail to detect coherent spoofing, creating a catastrophic false sense of confidence [PHASE1_BUILD_PLAN §4]. Detecting this load-bearing failure mode requires continuous, automated cross-family comparison against error-independent non-RF navigation sources (e.g., INS dead-reckoning, eLoran, radar fixes, and OCXO clock holdover) [OPNAVINST 9420.1C Encl 2; NIST IR 8323r1 p.22].

### 1.3 Proposed Software Innovation & Strict Scope Boundaries
In direct alignment with DON26BX05-NP004, our innovation is a **unified, ECDIS-like APNT operational awareness and decision-support software console**—a single-pane-of-glass operator interface providing rapid anomaly triage, composite confidence assessment, and explainable recovery guidance [DON26BX05-NP004 Description; Q&A 8/26/26]. 

**Air-Gapped & Local AI/UI Stack:** The complete software stack—including data ingestion, analytic correlation engines, local vector search (`lume serve`), local LLM rationale synthesis, and the WebGL/HTML5 user interface—operates **100% locally in an air-gapped container environment** with zero external network calls, zero cloud dependencies, and complete egress isolation [Q&A 8/28/26; PHASE1_BUILD_PLAN §5].

**Secured Runtime & Security Gate:** The architecture incorporates NIST SP 800-190 container security controls (unprivileged user execution, read-only root filesystems, dropped Linux capabilities, zero SSH/remote daemons) and an automated **pre-execution security verification gate** (Iron Bank readiness audit, SBOM verification, static vulnerability scan, and egress block check) [PHASE1_BUILD_PLAN §5]. This provides a verified hardening-ready security posture without claiming formal ATO, accreditation, or CMMC certification is already achieved [NP004 Filing Outline].

**Scope Boundaries:** Per topic mandates, this project **does not** develop new PNT/APNT sensors, physical timing hardware, navigation filtering algorithms, or autonomous ship control systems [DON26BX05-NP004 Description]. All recommended Courses of Action (COAs) are strictly **informational and advisory**; the software does not auto-route or actuate platform controls [PHASE1_BUILD_PLAN §2; Q&A 8/26/26]. The underlying simulator and scenario driver serve purely as internal feasibility and evaluation infrastructure, not the commercial product [PHASE1_BUILD_PLAN §0].

### 1.4 The Kobayashi Maru Evaluation Concept: Decision Under Uncertainty
Evaluating APNT decision support requires testing under severe, progressive PNT degradation where available information is incomplete or contradictory—a *Kobayashi Maru* problem-solving framework [ASSIGNMENT.md]. 

When EW jamming degrades primary GNSS and spoofing induces cross-family divergence, forcing a binary "correct" source selection creates brittle automation that risks driving a ship off-course. Our software implements an auditable decision logic that:
1. **Assesses Knowns & Exposes Assumptions:** Derives explicit single-source health and normalized composite confidence levels across 3–8 disaggregated streams (1–10 Hz) using ASPN/pntOS standard interfaces [Q&A 8/25/26; Q&A 8/26/26].
2. **Emits Explicit Uncertainty (`INDETERMINATE` State):** When sensors provide conflicting evidence that cannot be resolved with high confidence, the system surfaces an `INDETERMINATE` state and presents verification COAs (e.g., "Cross-check radar fix," "Confirm INS holdover") rather than forcing a low-confidence binary selection [PHASE1_BUILD_PLAN §2; Q&A 8/26/26].
3. **Presents Balanced Scenario Suite:** The Phase I evaluation harness executes reproducible scenarios spanning **Nominal** baselines, **Recoverable Faults/Jamming**, **Coherent Spoofing**, and **Held-Out Ambiguous (No-Win) Cases** to rigorously measure decision accuracy without rewarding permanent safety-abstention [ASSIGNMENT.md; PHASE1_BUILD_PLAN §5].

# 2. Phase I Technical Objectives & Key Performance Parameters (KPPs)

### 2.1 Phase I Technical Objectives
The overarching goal of the Phase I effort is to establish the technical feasibility of an air-gapped, containerized APNT decision-support console that ingests multi-source navigation streams, triages complex anomalies, and accelerates operator action under strict subsecond and security constraints [DON26BX05-NP004 Phase I; Q&A 8/28/26].

*   **Objective 1: Multi-Source Data Ingestion & Schema Normalization.** Ingest 3 to 8 disaggregated PNT data streams at 1 to 10 Hz over a local containerized pub/sub bus using open ASPN (YAML) and pntOS standard data structures [Q&A 8/26/26; ION GNSS+ 2023]. Normalize incoming source health, RAIM/HPL, C/N0, AGC, and solution status into standard assurance levels (Assured, Inconsistent, Unassured, Unavailable) [DHS PNT CF v2.0 §4; PNT-Integrity C4].
*   **Objective 2: Strict Subsecond Anomaly Triage & Composite Confidence Core.** Implement a deterministic, rule-based two-tier analytic core evaluating intra-family plausibility and cross-family agreement [PHASE1_BUILD_PLAN §5]. Compute a transparent composite confidence score and triage operational states (Nominal, Hardware Fault, RF Jamming, Coherent Spoofing, Indeterminate) within a **hard subsecond latency limit (< 1,000 ms)** from pub/sub ingress to rendered BAM alert banner and initial COA card, with **zero percentile miss allowance** [Q&A 8/25/26; NP004-ARCH-02]. Detailed rationale and evidence trees are delivered asynchronously via progressive-disclosure operator drill-down [Q&A 8/25/26].
*   **Objective 3: ECDIS-Conformant UX/HMI & Air-Gapped Local Stack.** Design an operator interface adhering to ECDIS presentation conventions for high operator familiarity, MIL-STD-1472H HSI standards, and MSC.302(87) Bridge Alert Management (BAM) prioritization [Q&A 8/28/26; MIL-STD-1472H §5.2; MSC.302(87) §6]. Execute the entire application and AI retrieval engine locally in an air-gapped runtime with zero cloud egress [Q&A 8/28/26].
*   **Objective 4: Secured Container Runtime & Pre-Execution Verification Gate.** Deploy all software modules inside hardened, unprivileged OCI container images conforming to NIST SP 800-190 guidelines [PHASE1_BUILD_PLAN §5]. Integrate an automated **security verification gate** in the build/deployment pipeline (vulnerability scanning, SBOM check, egress block validation) establishing Iron Bank hardening readiness without claiming prior ATO or CMMC accreditation [NP004 Filing Outline].
*   **Objective 5: Reproducible Evaluation Harness & Feasibility Demonstration.** Deploy a containerized simulation arena generating reproducible Destroyer strait-transit scenarios with ground-truth labels strictly isolated from system inputs [PHASE1_BUILD_PLAN §1]. Evaluate operator speed-to-decision, triage accuracy, and cognitive workload reduction across nominal, degraded, and held-out ambiguous scenarios without requiring human subject IRB approvals [Q&A 9/1/26; ASSIGNMENT.md].
